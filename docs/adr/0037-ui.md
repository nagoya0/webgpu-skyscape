# 37. The UI: a header and a settings window, built with Preact

- Status: Accepted
- Date: 2026-10-08
- Supersedes [ADR 0019](0019-no-ui-until-features-are-in.md) (no UI until the features are in)

## Context

[ADR 0019](0019-no-ui-until-features-are-in.md) kept on-screen controls out until the features
were in, with settings given as URL parameters. The maintainer now judges the features complete
enough that, once the presentation is tidied, the demo can be published, and wants to start the
UI (2026-10-08). Being publishable is a requirement.

The maintainer described the UI:

- A header, one line high, above the 3D view. It does not lie over the view: the view is made a
  little shorter to make room. On the left the frame rate; in the middle the title "WebGPU
  Skyscape Demo"; on the right a settings button and the credit "@nagoya0", plain text, beside a
  GitHub icon that alone links to the repository (https://github.com/nagoya0/webgpu-skyscape).
- The settings button dims the 3D view a little and opens a settings window in the middle of the
  screen. The settings now given as URL parameters move there and can be changed while the demo
  runs.
- A debug switch in the settings shows the debug text now in the top right corner, rebuilt with
  the UI framework.
- The loading screen and the screen shown where the demo cannot run are rebuilt with the UI
  framework too.

Claude proposed Preact with Signals, Lit, plain DOM, Svelte, React with a component kit, and
debug panels such as Tweakpane, and recommended Preact with Signals: the components are written
compactly, and settings held as signals can be read by both the UI and the render loop, so a
change reaches the next frame without rebuilding the UI. Lit was the second choice; plain DOM
would scatter the state of several dozen settings; debug panels look like development tools,
which ADR 0019 wanted to keep out of the final UI.

## Decision

Chosen by the maintainer:

- **Preact with Signals** for the UI.
- **The layout above**: the header, the settings window over a dimmed view, the debug window, the
  loading screen and the screen for unsupported browsers, all built with it.
- **Every setting in the window changes while the demo runs.** At first, settings that need a
  reload were to be in the window too, applied by a reload the window offered; as settings were
  moved, the maintainer took out the ones that needed it (the clouds on or off, the wind, the
  lens flare, the water drops), and the reload went with them (2026-10-08).
- **Development parameters**: those rarely used are removed; those still used stay as URL
  parameters that the UI does not show.
- **The settings window has two tabs**, the settings and the credits; **the data credits are in
  the credits tab**, no longer in the corner of the 3D view (the maintainer, 2026-10-08). GSI
  asks for its name and a link to its tile list page, without a place on screen (checked
  2026-10-08 at https://maps.gsi.go.jp/development/ichiran.html); the municipal boundaries are
  CC BY 4.0, which asks for credit in a manner reasonable for the medium.
- **The flight holds while the settings window is open** (the maintainer, 2026-10-08); the scene
  is still drawn, so changes show at once, and closing the window goes on as before.
- **In the settings tab** (the maintainer, 2026-10-08): the time of day is a field like the date;
  pausing is a switch named 一時停止 (on holds the flight); the position on the course is named
  コース行程 and is a slider without a number; the field of view and the exposure are not shown (they stay URL
  parameters); the lens flare and the water drops are always on, with no switch, and their URL
  parameters (`flare`, `drops`) are removed. Switching the clouds off is not shown either;
  `?clouds=0` stays for development, as it removes the clouds' cost and the haze, which
  `coverage=0` does not: it measures what the clouds cost and clears the view of the terrain.
  The wind is not shown; it stays a URL parameter.
- **The cloud settings' names** (the maintainer, 2026-10-08): the cloud amount of ADR 0033 is shown
  as 雲の大きさ (the size of the clouds), as it mostly changes how large they are; the coverage as
  雲の量, after 雲量 (cloud cover), the share of the sky the clouds cover. The coverage is a
  threshold on the weather map, not that share itself, so 雲の量 is a slider without a number. The
  code and the URL keep takram's names
  (`cloudamount`, `coverage`).
- **The debug window** (the maintainer, 2026-10-08) shows rendering figures, measured only while
  it is shown: under Scene the flight time; under Graphics the frame time, CPU (JS) and JS heap,
  GPU time and GPU memory (est.), triangles (in K or M), resolution (with the device pixel ratio as DPR when it is not 1) and draw calls. The labels say what is
  measured: the frame time follows the display's refresh; CPU (JS) is this page's JavaScript for
  a frame; the GPU memory is what three.js has allocated, not what the driver uses. The load
  factor moved to the HUD as Current G; the height and the cloud density left the screen (the
  cloud figures stay in `window.__debug`).
- **The loading screen** (the maintainer, 2026-10-08) covers the 3D view only, in the settings
  window's look without a frame, title or logo: what is being done, in English (the viewer only
  watches), above one progress bar for the whole start. The settings button cannot be pressed
  until it is gone. The start is complete when every stage is: WebGPU, the data (clouds, HUD,
  flight path), the shaders, the terrain seen from the start, and a few frames for the clouds'
  temporal upscaling and the anti-aliasing to settle. Only the terrain, loaded from GSI, may stop
  progressing; it counts as loaded when its queue has stayed empty for 1.5 s, or after 15 s
  without a new tile, as the coarser tiles already loaded stand in (the maintainer chose a
  time-out in that stage over one for the whole start).
- **The screen for when the demo cannot run** (the maintainer, 2026-10-08) is in Japanese, as the
  viewer reads it and acts on it: what is wrong and what to do, with technical details (missing
  GPU features, an error) left in English. No link to the README: the header links to the
  repository. Over the 3D view, like the loading screen; it offers a reload where that may help
  (a renderer that did not start, a lost GPU device, a failed start).
- **The window keeps the size of its larger tab** when the tab changes (the maintainer,
  2026-10-08).
- **The default scene time is 14:30 JST** (the maintainer, 2026-10-08; 16:30 before).
- **No area setting** while there is one area ([ADR 0036](0036-remove-the-tokyo-area.md)).
- **The look**: a subdued dark one: dark panels and light text, apart from the HUD.
- **The UI's text is in Japanese.** The title stays in English. The HUD, which imitates the
  aircraft's display, stays in English, including the lines fixed to the screen
  ([ADR 0034](0034-hud.md)).

## Consequences

- The repository is in English except for the Japanese text the UI shows (CLAUDE.md).
- URL parameters stay for the hidden settings and for reproducible checks
  ([docs/upgrading.md](../upgrading.md)); all of them remain ASCII only.
- The UI is drawn as HTML over the canvas, so recordings of the canvas show the HUD but not the
  UI.

### Implementation details, not discussed

- Japanese text uses the system's Japanese fonts (Hiragino, Yu Gothic, Meiryo, Noto Sans JP), so
  no font of several megabytes is loaded.
- The GitHub icon is GitHub's mark from Octicons (MIT).
- The frame rate is averaged over half a second.
- The settings tab (2026-10-08): the date and time of day, pausing and the position on the
  course, the HUD, the cloud amount, the cloud coverage and the debug window (the cloud amount only
  sets the power the weather map is raised to, a uniform). The wind would have needed a reload:
  the clouds' position is the wind times the time, so changing it while flying would move them
  all at once.
- The window's settings start from the URL parameters and are not written back to the URL
  (`src/ui/settings.ts`).
- The two tabs share one place in the window, the one not shown hidden, so the window keeps the
  larger size.
- The loading stages' shares of the bar (`LOADING` in `src/main.ts`) are provisional: WebGPU 5 %,
  data to 25 %, shaders to 40 %, terrain to 90 %, the settling frames (30) the rest. The terrain's
  share grows as 1 - exp(-ready tiles / 60), as the number of tiles needed is not known in
  advance; the bar never goes back.
